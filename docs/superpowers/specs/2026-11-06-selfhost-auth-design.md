# Self-host режим: авторизация и закрытые профили

Дата: 2026-11-06. Статус: дизайн одобрен в чате, спека ждёт ревью.

## Цель

Дать возможность хостить Docket на сервере так, чтобы без входа ничего не было доступно, а у каждого профиля были свои данные под паролем. Локальный режим (без входа) остаётся без изменений.

## Решения

- Режим включается `DOCKET_MODE=selfhost`. Значение по умолчанию `local`: поведение как сейчас.
- У каждого профиля свои данные: проекты, задачи, MCP-токен, настройки.
- Профили создаёт админ по инвайтам. Самостоятельной регистрации нет.

## Подход: отдельная SQLite на профиль + диспетчер перед `Router`

Отвергнуто:
- Общая БД с `user_id` во всех таблицах: правка каждого запроса и CHECK-ов на `actor IN ('denis','claude')`, высокий риск утечки между профилями.
- Только reverse-proxy с auth: нет профилей и данных по пользователю.

### Хранилище

`auth.db` (рядом с `DOCKET_DB`, например `/data/auth.db`):

| Таблица | Поля |
|---|---|
| `users` | `id`, `username` (уникальный, без учёта регистра), `password_hash` (PBKDF2-HMAC-SHA256, 600000 итераций, stdlib `crypto/pbkdf2`, без новой зависимости), `is_admin`, `created_at` |
| `sessions` | `token_hash`, `user_id`, `expires_at` (30 дней) |
| `invites` | `token_hash`, `created_by`, `expires_at` (7 дней), `used_at` |

Данные пользователя: `/data/users/<id>.db`. Файл открывается лениво через `store.Open`, у профиля свои `Service` и `events.Bus`. При создании профиля `profile_name` = логин, шаг имени в онбординге пропускается.

### Диспетчер

Новый пакет `internal/auth` и обёртка над `httpapi.Router`:

- Без сессии доступны: `/healthz`, статика SPA, `/api/auth/*`.
- `/api/*` (кроме `/api/auth/*`) и `/mcp`: запрос идёт в `Router` пользователя, собранный из его `Service`. Хендлеры не меняются.
- Сессия: cookie HttpOnly, SameSite=Lax, Secure при HTTPS (`r.TLS` или `X-Forwarded-Proto`). В БД только хэш токена.
- `/mcp`: bearer-токен ищется среди профилей по `Service.MCPToken`. Токен одного профиля не открывает данные другого. Упрощение: перебор профилей, годится для десятков пользователей; при росте заменить индексом токен-хэш → пользователь в `auth.db`.
- Браузерная навигация на `/mcp` с `Accept: text/html` отдаёт SPA, как сейчас.

### Первый запуск

Пока в `users` пусто, сервер пишет в лог одноразовый setup-код. `POST /api/auth/setup` с кодом создаёт первого пользователя-админа. После создания эндпоинт отвечает 404. Создание защищено транзакцией от гонки.

### API

- `GET /api/auth/me`: в `local` режиме 200 `{"mode":"local"}`; в `selfhost` с сессией 200 `{"mode":"selfhost","user":{...}}`, при пустой БД 200 `{"mode":"selfhost","setup":true}`, иначе 401.
- `POST /api/auth/login`, `POST /api/auth/logout`, `PUT /api/auth/password`.
- `POST /api/auth/setup` (setup-код + логин + пароль).
- `POST /api/auth/invite/{token}` (логин + пароль): принять инвайт.
- Только для админа: `GET/POST /api/admin/invites`, `GET /api/admin/users`, `DELETE /api/admin/users/{id}` (удаляет и файл БД; админ не может удалить себя).

### Защита

- Лимит попыток входа по IP и логину в памяти: 5 неудач за 10 минут, затем блок.
- Сравнение хэшей за постоянное время, пароль минимум 10 символов.
- Существующие Host- и Origin-проверки остаются. В `DOCKET_ALLOWED_HOSTS` нужно добавить реальный домен (описать в README).

### Фронтенд

- Экраны: вход, первый запуск, принятие инвайта (`/invite/<token>`).
- Раздел "Пользователи" в `AppSettings` для админа: список, создание ссылки-инвайта, удаление. Кнопка выхода для всех.
- Любой 401 от API возвращает на экран входа. В `local` режиме `/api/auth/me` отвечает "авторизация не нужна", UI не меняется.

### Остальное

- `maintenance` и бэкапы идут циклом по профилям, у каждого свой каталог в `DOCKET_BACKUP_DIR`.
- `DOCKET_SEED` в `selfhost` игнорируется.
- README и `docker-compose.yml`: запуск за HTTPS-прокси, порт не пробрасывать на `0.0.0.0` без него.

## Тесты

- Хэш пароля и проверка, одноразовость и срок инвайта.
- Setup-код работает только пока нет пользователей.
- Без сессии `/api/tasks`, `/api/events` и `/mcp` отдают 401.
- Задача профиля A не видна B; MCP-токен A не открывает данные B.
- Лимит попыток входа блокирует после порога.
- `local` режим работает как раньше (существующие тесты проходят без изменений).

## Вне рамок

Сброс пароля по почте, OAuth, 2FA, общие проекты между профилями, роли кроме админа.
